# 素材ライブラリ設計

Date: 2026-10-07
Status: ローカルWeb先行の方針は合意済み。ローカル版を実装し、[段階プロンプト](web-phases/README.md)に沿って検証。クラウド/iOS接続は後工程。

## 目的と現在の実装
個人の写真・画像・制作素材を追加、保管、整理、検索、閲覧するライブラリ。将来はWebとネイティブiOSから同じライブラリを使う。AIは後から追加する。

最初はPC上のWebアプリ、テスト用フォルダ、内部SQLiteで使い勝手を検証する。標準の保管先はローカルを維持し、共有する原本だけリモートへ明示的に移す。名前は未決定で「Asset Library」は仮称。リポジトリ名・Bundle IDは変更しない。

これは素材UIと現行ローカル版の設計の正本。次期の原本保管・所在・端末保持・転送については[保管設計](STORAGE-DESIGN.md)を正本とする。以下の専用コピー保存は現行実装の記録であり、参照登録への移行を同文書で定める。実装済み機能と制限は [CURRENT.md](../CURRENT.md)、実構成は [ARCHITECTURE.md](../ARCHITECTURE.md)、既存iOS写真設計は [DESIGN.md](DESIGN.md)。既存iOSとWebは当初別のDB・保存領域を持ち、自動同期しない。

## 初期版の範囲
| 項目 | 初期仕様（提案） |
| --- | --- |
| 対象 | 写真・画像。JPEG/PNGを登録・表示の必須形式とする |
| 追加 | ファイル選択、複数選択、ドラッグ＆ドロップ、指定テストフォルダの明示的な取り込み |
| 保管 | 現行は専用コピー保存。次期は登録ディレクトリへの参照を標準とし、共有する原本を確認後にリモートへ移す |
| 閲覧 | サムネイル一覧、拡大詳細、原本ダウンロード |
| 整理 | 名前・メモ編集、タグ、コレクション、お気に入り |
| 検索 | 名前・元ファイル名・メモ・タグ、種別・コレクション・お気に入りの絞り込み |
| 並び順 | 追加日時、名前、撮影日時。撮影日時が不明なら追加日時を使う |
| 削除 | 確認付きごみ箱移動、復元、確認付き完全削除 |
| 永続化 | 再起動後もファイル・整理情報を保持 |

HEIC/WebPは原本登録・ダウンロードを許可する候補とし、プレビュー生成は実装開始時のローカル実行環境で検証する。生成できない場合も原本を保持し、形式アイコンと理由を表示する。プレビュー非対応を素材破損として扱わない。

3Dモデル・EXR・マテリアルセットの専用取り込みと表示、AI解析・生成・Embedding、複数端末同期、公開共有、常時フォルダ監視は初期範囲外。初期対象形式の最終確定は実装前に行う。

## 画面と使い方
| 画面 | 内容 |
| --- | --- |
| ライブラリ | 全素材・お気に入り・コレクション・ごみ箱のナビゲーション、検索、絞り込み、グリッド |
| 追加 | 選択ファイル、処理進捗、成功・重複・失敗の件数、失敗項目の再試行 |
| 詳細 | 大きなプレビュー、名前、タグ、メモ、サイズ、形式、撮影日時、所属、ダウンロード |
| コレクション | 作成・名前変更・所属追加/解除。コレクション削除では素材を削除しない |
| 設定 | 保存先の表示、使用量、明示的なフォルダ取り込み、バックアップ案内 |

素材追加 → サムネイルで探す → 詳細で確認 → タグやコレクションで整理 → 原本を取り出す、を最優先の操作経路とする。失敗は項目ごとに表示し、成功した素材を巻き戻さない。検索条件は一覧と詳細の往復で保持する。

PCはドラッグ＆ドロップとキーボード操作、狭い画面は大きなタップ領域と折りたたみナビゲーションを使う。フォーカス表示、ラベル、キーボードでの詳細開閉を初期から確認する。将来のiOS版はSwiftUIを維持し、Webの画面をそのまま埋め込まず、写真選択・共有からの追加・スワイプに合わせる。

## ローカル構成と責務
```text
Browser → Local API → AssetService
                         ├─ AssetRepository → SQLite
                         ├─ AssetStorage → 管理ファイル
                         └─ PreviewGenerator → 派生画像
```

APIとDB・ファイル操作はPC上で実行する。ブラウザ内DBを素材情報の正本にはしない。ブラウザはAsset ID/File IDでアクセスし、絶対パスを受け取らない。ファイル保存とメタデータ保存の境界を分けるが、将来の全AWSサービスを模した仕組みは作らない。

採用構成はTypeScript/React/ViteのWeb UI、Python/FastAPIのローカルAPI、標準SQLite、Pillow。現在の署名Lambdaをローカル素材APIとして流用しない。依存はWeb lockfileとPython requirements.lock.txtへ固定。HEICは原本保管のみ、JPEG/PNG/WebPは派生生成する。撮影日時のEXIF抽出は未実装で並び順は追加日時へフォールバックする。

配置は `web/`（UI）、`local-api/`（APIと永続化）、`contracts/`（API仕様と例）。既存 `backend/` はAWS署名APIとして残す。

開発データは `.local/asset-library/` 配下の `library.sqlite3`、`objects/`、`staging/`。入力素材は `.local/fixtures/` に置き、全体をGit除外する。リセットはこの専用領域だけを対象とし、元素材フォルダを削除しない。

## データモデル
| Entity | 主な項目・役割 |
| --- | --- |
| Library | id、ownerId、schemaVersion。ローカルでは固定の開発用所有者 |
| Asset | id、libraryId、kind、name、note、source、createdAt、updatedAt、capturedAt（任意）、favorite、revision、state、trashedAt、archivedAt |
| AssetFile | id、assetId、role、originalFilename、objectKey、mimeType、byteSize、sha256、width/height（任意）、state、error |
| Tag / AssetTag | タグ名と素材との多対多関係 |
| Collection / CollectionAsset | コレクションと素材との多対多関係 |
| ImportJob / ImportItem | バッチ内の進捗、失敗、再試行、登録済みAssetとの対応 |

一つのAssetに複数のAssetFileを持たせる。初期のroleはoriginal/thumbnail/displayだが、全素材に3ファイルを強制しない。originalが保存できれば登録を成立させ、派生生成失敗は別状態で再試行できるようにする。

kindはphoto/image/texture/model3d/materialを将来追加可能な文字列として扱う。初期UIはphoto/imageのみ。sourceはimport/generatedなどの入手経路で、kindと分離する。photoは写真として指定・判別された画像、判別できない画像はimageとする。

objectKeyの案は `libraries/{libraryId}/assets/{assetId}/files/{fileId}`。タグや名前の変更でキーを変えない。ローカルの物理パスはStorageだけが解決し、外部から任意キー・パスを指定させない。従来のiOSキーとは異なるため、自動互換を前提にしない。

日時はUTCで保存し表示時に変換する。画像の幅・高さは任意。SQLiteのschemaVersionとAPIのversionは別管理し、外部キー、必須条件、トランザクションを使う。JSONをメタデータ拡張に使っても、タグ・所属・検索対象を巨大なJSON一つに閉じ込めない。

AI用の空テーブルやEmbeddingを今から作らない。後でAssetに紐づく解析結果を追加し、ハッシュ・解析目的・モデル・指示バージョンごとに再利用する。生成物は通常Assetとして登録し、生成元との関係を別途追加する。

## 追加・重複・削除の整合性
追加はstagingへコピー → サイズ・形式・SHA-256検証 → 重複確認 → 原本の管理領域配置 → DB登録 → 派生生成、の順とする。これは現行コピー取り込みの経路。次期のフォルダ参照登録は[保管設計](STORAGE-DESIGN.md)に従い、元の所在を記録して複製を避ける。初期の上限案は原本1件100MB。これは将来の3D素材の上限を決定するものではない。

同じライブラリの原本SHA-256が一致した場合は新Assetを作らず、既存素材へのリンクを結果に表示する。並行追加でも重複を防ぐよう原本ハッシュに一意制約を設ける。ごみ箱内で一致した場合は勝手に復元せず、復元操作を案内する。バッチの再試行は同じImportItem IDを使う。

DBとファイル操作は単一トランザクションにできない。ImportItemに処理状態を残し、起動時に未完了を照合する。DBだけ登録された欠損はエラー表示し、余剰ファイルは調査対象として記録する。失敗時に元素材を消さず、原本保存完了前にstagingを解放しない。

削除はまずごみ箱状態にする。通常の一覧から除外し復元を可能にする。完全削除はdeleting状態を永続化 → 管理ファイル削除 → DB関連行削除で、途中失敗を再試行する。派生だけ削除しても原本から再生成できる。入力フォルダは削除対象外。

ローカルのバックアップは、書き込みを停止した状態でSQLiteと原本・関連ファイルを同じ時点で退避する。派生は再生成可能。JSONだけでは原本を復元できない。初期版ではバックアップの手順を実装時に文書化し、自動クラウドバックアップは別工程とする。

## APIの契約案
すべて `/api/v1` 配下。同じoriginから利用し、一覧はページ分割する。初期検索はSQLiteによる文字列検索で、類似検索は行わない。

| 操作 | Endpoint案 |
| --- | --- |
| 一覧 / 詳細 | GET /assets、GET /assets/{id} |
| 追加 / 進捗 | POST /imports（ファイル）、GET /imports/{id} |
| テストフォルダ追加 | POST /fixture-imports（設定済みフォルダのみ） |
| 整理 / ごみ箱 / 復元 | PATCH /assets/{id}、POST /assets/{id}/trash、POST /assets/{id}/restore |
| 完全削除 | DELETE /assets/{id} |
| ファイル取得 | GET /assets/{id}/files/{fileId}/content |
| タグ / コレクション | GET/POST /tags、GET/POST /collections、PATCH/DELETE /collections/{id} |

PATCHの所属はtagIds/collectionIdsで更新する。Asset.revisionを送り、古いrevisionの変更は409で返して再読み込みを促す。初期でも複数ブラウザタブ間の上書きを防ぐ。リストはlimitとcursor、固定した並び順とIDを使い、ページ重複を抑える。

エラーはcode/message/itemId（必要時）を返す。分類は形式非対応、サイズ超過、容量不足、重複、欠損、競合など。トークン・絶対パス・内部スタックは表示しない。将来S3での配信に変えても、UIはFile IDから一時的な取得先を要求し、URLを永続保存しない。

## ローカルと本番の境界
初期は127.0.0.1だけで待ち受け、本人のPCで利用する。ログインは省略し固定の開発用所有者を使う。LAN公開やiPhoneからの接続はこの段階に含めない。本番設定で開発用所有者へフォールバックさせない。

ローカルでも許可origin/Hostを制限し、書き込みAPIは別サイトからのリクエストを拒否する。ファイル名を物理パスに直接使わず、パストラバーサル、シンボリックリンクによる保存領域外へのアクセス、任意フォルダ取り込みを防ぐ。

クラウドでは本人認証・認可・HTTPSを必須とする。既存iOSのCognito本人限定方針を引き継ぐ候補だが、Web用クライアント・コールバック・セッション保管は別設計する。公開前に認証設計と検証を完了する。

## 実装と移行の順序
| 段階 | 内容 | 完了の条件 |
| --- | --- | --- |
| L1 | ローカル起動、JPEG/PNG追加・永続化・一覧・詳細・原本取得 | 再起動後も閲覧でき、元素材のバイト列が変わらない |
| L2 | タグ・検索・コレクション・お気に入り・ごみ箱、追加エラー回復 | 実際のテスト素材で主要操作を一巡できる |
| L3 | レスポンシブ、ページ分割、形式対応検証、バックアップ手順 | 1,000件のテストデータで操作と計測結果を記録 |
| C1 | 移行用エクスポートと非公開S3保存 | ID・キー対応・ハッシュ・件数を照合し、原本照合と所在保持、共有登録前にローカルを削除しない |
| C2 | Web配信・APIホスティング・共有メタデータ・本人認証 | ローカル認証省略がなく、追加・整理・削除がクラウドで成立 |
| I1 | 既存iOSモデル移行、共通API接続、端末キャッシュ | Webの変更がiOSに反映され、逆方向も検証できる |
| A1 | 必要なAI解析・検索・生成から順次追加 | 結果保存・再利用・利用量管理を含む |

C1はローカルAPIからS3を利用する中間段階で、Webの公開ではない。C2ではLambda/API Gateway等を候補とするが、ローカルSQLiteをそのままLambdaの永続DBに置かない。DynamoDB等の共有メタデータ保存先と検索方法はL3の利用結果を基に選定する。

クラウド移行はアダプター交換だけでは完了しない。既存データの移行、認証、配信、失敗回復、競合を別途設計する。共有素材の整理情報はオンラインAPIを正本としてrevision競合を検出し、ローカル所在と端末保持設定は各端末を正本とする。オフライン編集キューや自動マージは後の範囲とする。

既存iOSのPhoto・アルバム・version 1バックアップ・本人prefixは明示的に変換する。事前退避と変換検証を用意するまで既存DBを更新しない。既存署名APIの画像形式・3ファイル・100MB制約も別途変更が必要。過去のJSONをそのまま新Web DBへ復元できるとは扱わない。

## 検証と実装前の確認
ローカル版では登録→再起動→検索→整理→原本取得→ごみ箱→復元→完全削除を手動で確認する。原本ハッシュ、重複追加、部分失敗と再試行、DB移行、保存領域外アクセス、更新競合は意味のある自動テスト対象とする。

形式非対応、壊れた画像、空ファイル、容量不足、途中終了、欠損原本を確認する。1,000件で一覧初回表示・検索・スクロールを測定し、性能目標は実装開始時に検証PCの条件とともに定める。現在のSwift/iOSテスト成功を新Web版の検証結果として使わない。

実装前に決める項目は正式名称、初期形式の範囲、具体的なWeb/APIフレームワークと依存、テスト素材と性能目標。名称は後決めでも実装できる。AWS費用は保存量・アクセス量を測定して作成直前に見積もり、月額目標を保証値にしない。

実際の起動手順は [OPERATIONS.md](../OPERATIONS.md)、検証入口は [TESTING.md](../TESTING.md)、実在する配置は [CODEMAP.md](../CODEMAP.md)。AWSサービスの作成はまだ行っていない。
